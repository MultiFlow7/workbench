# req-043 · 工具调用状态 UI 反馈

## 状态说明（2026-06-13）

本需求暂不做。原方案是 ChatView 内存态工具状态行；当前 UI 主路径已切到 ProcessTrace，工具调用可见性后续按 ProcessTrace 数据契约重新规划。

## 背景与目标

依赖 req-041 的 tool calling 闭环，当 AI 发起工具调用时，用户会看到对话「暂停」——无文字流出、输入框禁用——但不知道发生了什么。如果没有任何反馈，用户会以为程序卡死。

v0.11 目标：在 ChatView（P3）中给工具调用过程提供最小化的可见反馈，让用户知道「AI 正在用工具干活」。

## 设计方向

### 工具调用状态行

在 ChatView 的 streaming 区域（AI 回答气泡内，或气泡下方），当检测到 tool_call 时，展示一行状态提示：

```
⚙ 正在执行工具：read_file（"01-Vibe项目区/xxx.md"）...
```

- 工具名称和关键参数（如文件路径、命令前 40 字符）可见，让用户理解 AI 在做什么
- 使用旋转加载图标或 CSS 动画表示「进行中」
- 执行完成后，该行变更为「✓ 工具执行完成（Xs）」并保留在对话历史中
- 执行失败时，变更为「✗ 工具执行失败：[错误提示]」

### 样式约束

- 遵循工作台已有设计系统：字体 Inter，颜色 `--accent: #2563eb`，浅色主题
- 工具状态行视觉上区别于 AI 文字回答（使用略小字号 + 不同背景色），不与对话内容混淆
- 动效使用 CSS `cubic-bezier(0.4,0,0.2,1)`（功能型过渡，与面板折叠一致）

### 多次工具调用

单次对话中 AI 可能连续调用多个工具（如先 search_vault 再 read_file），每次调用各自显示一行状态。

## 待 CEO 确认

1. **工具调用历史是否持久化**：工具状态行（「✓ 执行完成」）是否需要写入 atom 的数据结构并持久化？还是仅在当前会话内存展示？v0.11 建议仅内存展示，不改数据模型，但需确认。
2. **工具调用中用户是否可中断**：当 AI 正在等待工具执行时，用户是否可以点击「停止」取消？v0.11 先不支持中断（输入框禁用到工具完成），后续版本再考虑。

## 验收指标

| 验收项 | 标准 |
|--------|------|
| 工具执行中有可见反馈 | 工具调用期间，ChatView 显示「正在执行工具：xxx」提示行，有动效 |
| 工具名称和参数可读 | 状态行展示工具名 + 关键参数（路径/命令摘要），不超出 ChatView 宽度 |
| 执行完成状态更新 | 工具完成后，状态行变更为「✓ 执行完成」并展示耗时 |
| 执行失败有提示 | 工具失败时，状态行变更为「✗ 失败：[原因]」，不崩溃 |
| 多轮工具调用各自显示 | 连续两次工具调用显示两行状态，不互相覆盖 |
| 样式与设计系统一致 | 工具状态行字体、颜色与已有 ChatView 设计规范一致，不突兀 |
